## Context

现有 `drama_featured_categories` 是无序多对多表，只允许 `hot / new / exclusive`。剧详情页通过一次替换某部剧的分类集合来写入；运营分类页按剧集更新时间排序后只读展示。单剧同步 payload 还携带分类数组，但它既不能表达分类内顺序，也无法在清空某个分类时形成完整快照。

仓库保持单进程 FastAPI 模型；业务同步已由 `sync_client` 统一处理地址、API key 和超时，并由 `can_sync` 权限控制。运营分类数据量很小，不需要复用媒体同步队列。

## Goals / Non-Goals

**Goals:**

- 将“推荐 / 最新 / 最热 / 独家”建模为四个固定、有序、可整体替换的剧单。
- 在一个后台页面完成查看、选中 / 反选、移除及排序。
- 保持剧详情页原有分类勾选入口可用，新加入的剧追加到对应分类末尾。
- 通过专用接口向业务服务器原子发布四个分类的完整有序快照。

**Non-Goals:**

- 不支持运营人员新建、重命名或删除分类。
- 不实现自动“最新 / 最热”算法；四类均为人工编排。
- 不为运营分类引入后台队列、重试状态机或自动同步；同步仍是显式操作员动作。
- 不在本仓库实现业务服务器接收端，只定义其线协议。

## Decisions

### 1. 关系表增加显式 `sort_order`

`drama_featured_categories` 增加非负整数 `sort_order`，主键仍为 `(drama_slug, category)`，并增加 `(category, sort_order)` 索引。每次分类级保存都在单个事务内删除该分类旧关系，再按请求数组的顺序写入连续的 `0..N-1`。

相比单独的“分类 + JSON slugs”表，关系表继续保留外键级联删除和高效的按剧反查；相比浮点 rank，连续整数更易验证，运营列表规模也足以承受整体替换。

已有无 `sort_order` 的表在 `init_db()` 中一次性重建：保留原关系，并按原总览排序规则（最近 ready 更新时间、剧更新时间、slug）生成稳定初始顺序；新表 CHECK 同时加入 `recommend`。这避免要求操作员删除现有业务数据。

### 2. 分类级 API 以完整 slug 数组为写入单位

新增 `GET /admin/featured-categories.json` 返回四类有序详情及可选剧列表；`PUT /admin/featured-categories/{category}` 接受 `{"drama_slugs": [...]}`。服务端校验固定分类、slug 格式、剧存在性并去重，然后原子替换。

完整替换天然覆盖添加、反选移除和排序，并避免多个细粒度 move API 产生中间状态。剧详情的既有 `PUT /admin/dramas/{slug}/featured-categories` 保留，但只增删该剧关系：保留其它成员顺序，新增成员追加到末尾。

### 3. 页面使用无依赖的模态框与上移 / 下移控制

运营分类页渲染四个模块。每个模块提供“添加 / 管理”按钮打开完整剧列表复选模态框；保存复选结果后返回模块列表。模块中的每部剧提供上移、下移、移除按钮，操作后提交完整有序数组。

不引入拖拽库，避免额外网络依赖及移动端可访问性问题；明确按钮同样满足排序需求，并能通过 disabled 状态表达边界。

### 4. 运营分类使用独立全量同步协议

新增受 `require_can_sync` 保护的 `POST /admin/featured-categories/sync`。启用业务同步时，它构建：

```json
{
  "categories": {
    "recommend": ["slug-a", "slug-b"],
    "new": [],
    "hot": ["slug-c"],
    "exclusive": []
  }
}
```

并通过现有 `sync_client` 调用业务服务器 `PUT /sync/featured-categories`。业务服务器必须在一个事务内校验所有 slug 已存在并整体替换四类；空数组表示清空。管理接口同步等待该轻量请求完成：成功返回 200，未配置返回 503，上游拒绝或网络错误映射为 502。

单剧 `POST /sync/dramas` 不再携带 `featured_categories`，从而明确专用快照是唯一发布路径，也防止后续单剧同步破坏人工排序。

### 5. 独立持久化运营分类同步脏状态

新增单行 `featured_category_sync_state` 表记录 `is_dirty`、本地修改时间和最近成功同步时间。分类级替换或剧详情分类编辑只有在最终有序成员确实变化时才在同一事务中标记 dirty；物理删除一个仍在分类中的剧也标记 dirty。向业务服务器同步成功后标记 clean，失败时保持 dirty。

页面根据该状态选择按钮样式：dirty 使用 `btn-primary` 高亮，clean 使用 `btn-secondary` 普通样式。按钮仍可在 clean 状态下手动再次同步，但重复保存完全相同的分类内容不会重新高亮。

## Risks / Trade-offs

- [业务服务器尚未实现新端点时同步会失败] → 后台明确显示失败信息；分类本地编辑不受影响，双方按线协议联调后再发布。
- [整体替换在超大剧库中写入较多] → 固定分类通常是小型运营集合；事务写入简单且一致性优先。
- [并发编辑最后写入者覆盖前者] → 当前后台无版本化编辑基础，采用与其它替换式编辑器一致的 last-write-wins；每次成功后刷新服务器状态。
- [旧表 CHECK 无法 ALTER] → 启动迁移采用事务式新表复制 / 替换，并添加迁移测试。
- [状态表首次部署时不知道远端快照] → 如果本地已有任一分类成员则初始化为 dirty，空分类库初始化为 clean。

## Migration Plan

1. 部署业务服务器 `PUT /sync/featured-categories` 接收端。
2. 部署 HLS 服务；首次 `init_db()` 自动重建旧关系表并生成顺序。
3. 运营人员检查四类初始顺序，添加“推荐”内容后点击专用同步。
4. 回滚代码时旧版本无法识别 `recommend` 和 `sort_order`；回滚前应备份 DB，并移除推荐关系后按旧 schema 重建关系表。
